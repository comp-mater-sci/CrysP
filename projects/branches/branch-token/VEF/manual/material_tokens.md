Usage of material tokens   {#page_material_tokens}
========================

Material tokens
---------------

Material Tokens are a digital protection measure that enforces authorized use of the 
Software according to the License Agreement. In particular, the Tokens are needed in 
any of the VEF analysis procedures. This manual covers technical aspects of using the 
material tokens in the VEF. Please consult License Agreement Annex IV for definitions 
and conditions of using the tokens.
 

Briefly, the Tokens are digital files that can be electronically transmitted and stored 
on User’s computer systems. A token may have one of the statuses:

* *Valid Token*: A Valid Token that remains at User’s disposal.

* *Expired Token*: An Expired Token is a Token that has not been used before its 
expiration date and cannot be used in VEF analysis procedures anymore.

* *In-use Token*: A Token that has been used by the User to sign texture datafile during
  importing an external texture datafile into the VEF.


Use of material tokens
----------------------

In normal circumstances the User only works with the 'In-use Tokens', whereas the 'Valid 
Tokens' and 'Expired Tokens' are internally handled by the token management system in 
the VEF software.


The User should understand that the following general rules apply:

1. Any VEF analysis procedure requires an 'In-use Token'  and a texture datafile signed
   with that token.
2. Any other usage of the Software does not require 'In-use Token'.
3. An In-use Token cannot be turned back into a 'Valid Token'.
4. 'In-use Token' does not expire.
5. Any texture datafile generated by the VEF analysis procedures is signed with the 
   'In-Use Token' used in that analysis. Therefore, such signed texture datafile _can later 
   be used_ by any VEF analysis procedure.
6. Any texture datafile generated by the Software but later modified by the User is 
   considered _as an external texture datafile_. Therefore, it needs to get imported
   into the software, which consumes another token.


At any time it is possible to check the current balance of tokens by using tool 
`check_tokens`. It reports the total number of tokens that were purchased and the 
number of 'Valid tokens' (reported as available tokens). The tool does not require any 
parameters.

       check_tokens

**Note**: it may take a while for `check_tokens` to return the output.


Typical procedure
-----------------

1. (optional) `odf2smt` is used to create discrete texture in SMT format. The discrete texture file 
   is then checked. For example:
   
       odf2smt --input AA5005.odf
   
   At this point no token is used yet. Although this step is optional, it
   is recommended to use it to prevent consuming a token on a texture that does not meet 
   user's requirements.

2. (optional) `check_tokens` is used to check if there are still 'Valid tokens' available.

       check_tokens

   This step is optional, but in certain situations it helps to avoid possible issues
   at later stages of the procedure.

3. `odf2smt` is used to create a signed discrete texture in SMT format. 

       odf2smt --input AA5005.odf --token_path=AA5005_token
   
   The command will produce three files:
   
   1. SMT file: `AA5005.smt`
   2. signature file `AA5005.smt.slissig`
   3. token file `AA5005_token` that contains an 'In-Use' token. 

4. `alamDMC` is used to run an analysis procedure. This step can be repeated with any
   analysis procedure as many times the User needs.

   For example, let's assume the `UDSA` module is used and the generic section of 
   the configuration file `AA5005_udsa.cfg` includes:
   ~~~~~~~~~~~~~~~~~~~~~{.txt}
    AA5005_UDSA          # Prefix for the output files
    True                 # Flag: request incremental output of the material state
    0                    # Verbosity level: 0 (the lowest) - 3 (the highest)
    AA5005.smt           # Path to the texture file
    ALAMEL               # Model type: either ALAMEL or FCTaylor
    fcc12                # Family of slip systems
    True                 # Flag: use default microstructural description
    True                 # Flag: use default hardening
   ~~~~~~~~~~~~~~~~~~~~~

   The texture file `AA5005.smt` and the signature file `AA5005.smt.slissig` must be
   located in the same directory. 
   
   The analysis is invoked using the command line:
   
       alamDMC  UDSA  AA5005_udsa.cfg  AA5005_token
   
   When the analysis is started, the signature file is checked. The analysis only 
   continues if the texture file is signed with the proper token.
   
   When certain analysis procedures are executed (such as UDSA, ASR, ADP), they may 
   provide a texture datafile (with extension .cur) with an evolved texture. Such 
   datafiles are automatically signed with the token used in the analysis.
   
   In the current example, the analysis will output:
   
   1) `AA5005_UDSA.cur` 
   2) `AA5005_UDSA.cur.slissig`
   
   
5. (optional) `alamDMC` is used to run another analysis procedure that starts from the 
   evolved texture.
   
   In the present example, let's assume the `YLD` module is used and the generic section 
   of the config file `AA5005_evolved_yld.cfg` includes:
   ~~~~~~~~~~~~~~~~~~~~~{.txt}
   AA5005_evolved_yld   # Prefix for the output files
   True                 # Flag: request incremental output of the material state
   0                    # Verbosity level: 0 (the lowest) - 3 (the highest)
   AA5005_UDSA.cur      # Path to the texture file
   1                    # Index of the block inside the CUR file
   ALAMEL               # Model type: either ALAMEL or FCTaylor
   fcc12                # Family of slip systems
   True                 # Flag: use default microstructural description
   True                 # Flag: use default hardening
   ~~~~~~~~~~~~~~~~~~~~~

   The token has to be provided in the command line that invokes the analysis:
   
       alamDMC  YLD  AA5005_evolved_yld.cfg  AA5005_token
